# מסמך חזרה: מ-`b/largpeami` חזרה לנתונים בשורש (`legacy`)

**מתי משתמשים בו:** אחרי שלארג' פעמי עבר למצב `b` (`b/largpeami.dataRoot == 'b'`), ומשהו לא עובד, ורוצים שהאפליקציה תחזור לעבוד עם הנתונים בשורש, כמו היום.

**למה זה בטוח:** הכלי אף פעם לא מוחק ולא משנה את הנתונים בשורש. לכן אחרי חזרה ל-`legacy`, השורש נמצא בדיוק במצב שבו היה ברגע המעבר. מה שנכתב בינתיים ב-`b/` נשאר שם, ולא אובד.

**נוסה באמולטור:** בדיקה 11 ב-`firebase/tests/migrate-tool.test.js` (הפלט בדוח השלב). בפרויקט אמיתי: לא נוסה.

## לפני המעבר ל-`b` (הכנה, פעם אחת)
1. מריצים גיבוי טרי: `backup --out backup-before-switch.json` (או התהליך ב-GitHub במצב `readonly`). שומרים את הקובץ ואת מספר ההרצה.
2. מריצים השלמה אחרונה (`copy --mode write`) ואימות (`verify`). ממשיכים רק אם האימות עבר ואין התנגשויות.
3. שומרים את קובץ המצב (`state.json`) מההעתקה האחרונה. הוא משמש בצעד 2 של החזרה.

## החזרה, צעד אחר צעד
1. **עוצרים כתיבה חדשה (מומלץ):** מבקשים מהמנהל והעובדים לא לעבוד באפליקציה בזמן החזרה (כמה דקות).
2. **דוח: מה נכתב ב-`b/` מאז ההעתקה האחרונה** (לא משנה כלום):
   ```bash
   node firebase/migrate/migrate.js report-since --project <PROJECT> --biz largpeami --state state.json --report since.json
   ```
   הדוח מציג מסמכים חדשים, מסמכים ששונו ומסמכים שנעלמו ב-`b/largpeami`, וגם קבצי Storage חדשים. שומרים אותו.
3. **מחזירים את `dataRoot` ל-`legacy`:**
   ```bash
   node firebase/migrate/migrate.js set-dataroot --to legacy --mode write --project <PROJECT> --biz largpeami
   ```
   הפקודה כותבת רק את השדה `dataRoot` במסמך `b/largpeami`, ורק אם המסמך קיים. (בפרויקט אמיתי, גם השומר חייב לעבור: משתני `MIGRATE_*`, ראו README.md.) אפשר לעשות את אותו הדבר ידנית במסוף Firebase.
4. **בודקים שהשורש שלם:**
   ```bash
   node firebase/migrate/migrate.js compare-backup --project <PROJECT> --backup backup-before-switch.json
   ```
   התוצאה צריכה להיות "המקור זהה לחלוטין לגיבוי". אם יש הבדלים, הם נובעים מכתיבה לשורש אחרי הגיבוי (למשל אפליקציה ישנה שעוד כותבת לשורש). הכלי לא כתב לשורש.
5. **האפליקציה:** פותחים את האפליקציה כמנהל וכעובד. היא קוראת את מסמך העסק בפתיחה, ועוברת לנתונים בשורש. בודקים שהנתונים מופיעים (שלב 3: כשל בקריאת מסמך העסק משאיר את לארג' פעמי ב-`legacy`).
6. **החלטה של המשתמש: מה עושים עם מה שנכתב ב-`b/` בינתיים** (לפי הדוח מצעד 2). הכלי **לא** מחזיר אותו לשורש אוטומטית. האפשרויות:
   - להזין מחדש באפליקציה את מה שחסר (מתאים לכמה רשומות).
   - להעתיק ידנית מסמכים מסוימים לשורש (דורש החלטה ואישור, כי זו כתיבה לשורש).
   - להשאיר ב-`b/` ולחזור ל-`b` אחרי התיקון. ההשלמה הבאה תדווח התנגשויות ולא תדרוס.

## חזרה ל-`b` אחרי התיקון
1. השלמה (`copy --mode write` עם אותו `state.json`), ואז `verify`. מסמכים ששונו בשני הצדדים יופיעו כהתנגשויות, וההחלטה בהם ידנית.
2. `set-dataroot --to b --mode write`.

## מה לא עושים
- לא מוחקים את `b/largpeami` ולא את השורש. גם לא "כדי להתחיל מחדש".
- לא מריצים `gcloud firestore import` בלי אישור: הוא דורס מסמכים.
