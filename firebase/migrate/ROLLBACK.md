# מסמך חזרה: מ-`b/largpeami` חזרה לנתונים בשורש (`legacy`)

**מתי משתמשים בו:** לארג' פעמי עבר למצב `b` (`b/largpeami.dataRoot == 'b'`), משהו לא עובד, ורוצים שהאפליקציה תחזור לעבוד עם הנתונים בשורש, כמו היום.

**למה זה בטוח:** הכלי אף פעם לא מוחק ולא משנה את הנתונים בשורש. לכן אחרי חזרה ל-`legacy`, השורש במצב שבו היה ברגע המעבר. מה שנכתב בינתיים ב-`b/` נשאר שם ולא אובד.

**איפה נשמר הגיבוי שלפני המעבר:** ב-bucket הפרטי של הפרויקט, בנתיב `migrate_backups/<זמן>_run<מספר ההרצה>/backup.json`. הנתיב המלא מופיע בסיכום של ההרצה שיצרה אותו (שורה "הגיבוי נשמר ב-bucket הפרטי של הפרויקט: gs://..."). הקובץ לא נשמר ב-GitHub ולא במאגר.

**נוסה באמולטור:** בדיקה 11 ב-`firebase/tests/migrate-tool.test.js`, כולל שמירת הגיבוי ב-bucket והשוואה מולו. בפרויקט אמיתי: לא נוסה.

כל הצעדים מתבצעים מהתהליך הידני ב-GitHub (Actions ← "Migrate largpeami data"), עם `project_id` שמוקלד פעמיים. בפעולות שכותבות צריך גם `write_confirm` = `write-to-<מזהה>`.

## לפני המעבר ל-`b` (הכנה)
1. `action=copy` (השלמה, עם `state_run_id` של ההרצה הקודמת עם `copy`). ממשיכים רק אם האימות עבר ואין התנגשויות. **רושמים את מספר ההרצה הזו**: זה `state_run_id` לצעדים הבאים.
2. `action=switch-to-b`. ההרצה שומרת קודם גיבוי טרי ב-bucket, ורק אחר כך משנה את `dataRoot` ל-`b`. **רושמים את נתיב הגיבוי** מסיכום ההרצה. זה `backup_path` לחזרה.

## החזרה, צעד אחר צעד
1. **עוצרים כתיבה חדשה (מומלץ):** מבקשים מהמנהל ומהעובדים לא לעבוד באפליקציה בזמן החזרה (כמה דקות).
2. **דוח: מה נכתב ב-`b/` מאז ההעתקה האחרונה.** הצעד לא משנה כלום. מריצים `action=report-since`, עם `state_run_id` של ההרצה האחרונה עם `copy`. הדוח מציג:
   - מסמכים חדשים, מסמכים ששונו ומסמכים שנעלמו ב-`b/largpeami`.
   - קבצי Storage חדשים.
   הדוח נשמר ב-artifact של ההרצה.
3. **חזרה:** `action=rollback-to-legacy`, עם `backup_path` (מצעד 2 של ההכנה) ועם `state_run_id`. ההרצה עושה שלושה דברים:
   - מריצה שוב את הדוח.
   - משנה רק את השדה `dataRoot` במסמך `b/largpeami` ל-`legacy`. השינוי מותר רק אם המסמך נוצר על ידי הכלי.
   - משווה את השורש לגיבוי שב-bucket.
   התוצאה הרצויה: "המקור זהה לחלוטין לגיבוי". אם יש הבדלים, הם נובעים מכתיבה לשורש אחרי הגיבוי (למשל מאפליקציה ישנה). הכלי לא כותב לשורש.
4. **האפליקציה:** פותחים אותה כמנהל וכעובד. בפתיחה היא קוראת את מסמך העסק, ועוברת לנתונים בשורש. בודקים שהנתונים מופיעים.
5. **החלטה של המשתמש: מה עושים עם מה שנכתב ב-`b/` בינתיים** (לפי הדוח). הכלי **לא** מחזיר אותו לשורש אוטומטית. האפשרויות:
   - להזין מחדש באפליקציה את מה שחסר (מתאים לכמה רשומות).
   - להעתיק ידנית מסמכים מסוימים לשורש. דורש החלטה ואישור, כי זו כתיבה לשורש.
   - להשאיר ב-`b/`, ולחזור ל-`b` אחרי התיקון.

(אפשר להשוות לגיבוי גם בנפרד: `action=compare-backup` עם `backup_path`.)

## חזרה ל-`b` אחרי התיקון
1. `action=copy` (השלמה). מסמכים ששונו בשני הצדדים יופיעו כהתנגשויות, וההחלטה בהם ידנית.
2. `action=switch-to-b`.

## הרצה מהמחשב (רק אם GitHub לא זמין)
אותם צעדים, עם המשתנים שבסעיף "הרצה מהמחשב" ב-README.md. כל הקבצים ב-`/tmp/lp-migrate/`, מחוץ למאגר:
```bash
node firebase/migrate/migrate.js report-since --project <PROJECT> --state /tmp/lp-migrate/state.json --report /tmp/lp-migrate/since.json
MIGRATE_MODE=write MIGRATE_WRITE_CONFIRM=write-to-<PROJECT> node firebase/migrate/migrate.js set-dataroot --to legacy --mode write --project <PROJECT>
node firebase/migrate/migrate.js compare-backup --project <PROJECT> --backup-gcs migrate_backups/<...>/backup.json
```

## מה לא עושים
- לא מוחקים את `b/largpeami` ולא את השורש, גם לא "כדי להתחיל מחדש".
- לא מריצים `gcloud firestore import` בלי אישור: הוא דורס מסמכים.
