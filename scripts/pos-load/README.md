# scripts/pos-load – נתוני דמו, בדיקת עומס ובדיקת כפילות לקופה

התיקייה הזו **לא** משתתפת בבניית האפליקציה ולא נוגעת בפרויקט הייצור. היא רצה רק מול **אמולטור Firestore מקומי**
(פרויקט `demo-pos-load` – תחילית `demo-` = אין פנייה לשום שירות אמיתי). פרויקט הבדיקה `largpeami-test-f4691` נתמך רק בדגל מפורש,
ו-`largpeami` (ייצור) חסום בקוד (`lib/env.js`).

## הרצה
```
cd scripts/pos-load
npm install
./run-emulator.sh          # נתונים → אמולטור → בדיקות → דוח (כ-4 דקות)
```
דרוש: Node 20+, Java 21 (לאמולטור), python3. התוצאות: `out/results.json`, הדוח: `out/report.md`.
`python3 report.py --save` מעדכן גם את `RESULTS.md` (הדוח האחרון שנכנס למאגר).

**מעקף proxy (סביבת ענן):** `run-emulator.sh` מריץ את האמולטור בלי `JAVA_TOOL_OPTIONS` ובלי `HTTP(S)_PROXY`, ו-`lib/env.js`
מוסיף `127.0.0.1` ל-`NO_PROXY` ומבטל את ה-proxy של gRPC לפני שטוענים את firebase-admin. בלי זה החיבור לאמולטור עובר דרך המתווך ונכשל.

## הקבצים
| קובץ | מה יש בו |
|---|---|
| `gen-demo-data.js` | מחולל נתוני דמו דטרמיניסטי: 5,000 מוצרים (~10,800 וריאציות, ברקוד EAN-13 תקין בטווח 2xx הפנימי), 41 קטגוריות, 2,000 לקוחות, 4 סניפים, 525 מכירות לסניף ביום עם שיא של 60 בשעה. כל רשומה `demo:true`, כל שם מתחיל ב"דוגמה". `--seed-emulator` כותב לאמולטור תחת `b/demo-pos/`. |
| `lib/pos-sale-ref.js` | **מימוש ייחוס** של פונקציית המכירה לפי הממשק הצפוי (ראו למטה) – כדי שהבדיקות ירוצו כבר עכשיו. סופר קריאות וכתיבות. |
| `lib/pos-client.js` | בוחר מול מה בודקים: `POS_IMPL=ref` (ברירת מחדל) או `POS_IMPL=fn` – הפונקציה האמיתית דרך אמולטור הפונקציות. |
| `loadtest.js` | הבדיקות: כפילות (ברצף ובמקביל), 100 מכירות במקביל בלי חורים במספור (2 גרסאות), תור אופליין, יום מלא דחוס בזמן. |
| `report.py` | דוח ביצועים: זמן לכל מכירה, קריאות/כתיבות ליום מול המכסות, עלות. כל הערכה מסומנת **[הערכה]**. |
| `RESULTS.md` | הדוח של ההרצה האחרונה. |

משתני סביבה ל-`loadtest.js`: `POS_ONLY=1,3ב,5` (רק חלק מהבדיקות), `POS_COMPRESS` (דחיסת זמן, ברירת מחדל 720), `POS_PAR` (100),
`POS_MAX_ATTEMPTS` (5), `POS_SETTLE_MS` (הפסקה בין בדיקות, 15000), `POS_SEND_TIMEOUT_MS` (90000).

## הממשק הצפוי (⚠️ הנחה – פונקציות השרת של הקופה עוד לא קיימות ב-main)
```
posSale({ reqId, br, dev, lines:[{pid, vid, qty, price}], pay:{m, amt}, custId?, at }) → { id, no, total, dup }
```
- `reqId` נוצר במכשיר לפני השליחה (גם בלי אינטרנט). אותו reqId שוב → אותה מכירה (`dup:true`), בלי מספר חדש ובלי תנועת מלאי.
- מספור רץ לכל סניף ב-`b/{biz}/poscfg/seq_{br}`, בתוך טרנזקציה (כמו `ordcfg/seq` ב-`orders.js`).
- מכירה: `b/{biz}/pos/s{reqId}` · מלאי: `b/{biz}/stock/{br}_{pid}_{vid}` · סיכום יומי: `b/{biz}/posday/{br}_{yyyymmdd}`.

המבנה נבנה לפי הדפוס של `createCore` ב-`firebase/functions/orders.js`, כי התוכנית (`my-agents`) לא הייתה נגישה מהסשן.

## ⏳ ירוץ רק אחרי המיזוג של פונקציות הקופה (סשן ז')
1. להשוות את הממשק למעלה לפונקציה האמיתית (שם, שדות, נתיבים), ולעדכן את `lib/pos-client.js` אם צריך.
2. להריץ את אותן בדיקות מול אמולטור הפונקציות:
   `firebase emulators:exec --only auth,firestore,functions` מתוך `firebase/`, עם `POS_IMPL=fn POS_FN=<שם> node ../scripts/pos-load/loadtest.js`.
   צריך גם משתמש דמו עם הרשאת קופה בסניף (`users/{uid}`) – לפי מנגנון ההרשאות שסשן ז' יבנה.
3. במצב `fn` מספר הקריאות/כתיבות לא נמדד מבפנים – הדוח מסמן אותו כהערכה.
